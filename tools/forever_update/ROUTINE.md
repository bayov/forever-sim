# The daily WoW Forever update routine

The cloud routine "WoW Forever Daily Update" runs this every day at 19:53 Israel time. Its
trigger prompt only says to follow this file, so a change to the routine is a commit here.
It prepares work and never merges: a news report, a `forever-update/<date>` PR for the sim
and TASKS.md items. The local /update-data skill (in the WoW folder) lands the PRs with the
user's yes. Everything below is the routine's instructions, written to it.

---

Write me a daily news update on World of Warcraft: Forever (also called "WoW: Forever" or "Classic+"), Blizzard's new Classic-based version of WoW. Check which hidden items have been newly revealed, work out what each change means for my sim (forever-sim), open a pull request with the sim changes, log follow-up work in the repo's TASKS.md, and publish the report as an HTML artifact. The beta started September 17, 2026 and ends around October 21–22, 2026; the game launches live on November 4, 2026. This task must work both during the beta and after launch: search to find out which phase the game is in today, and cover beta builds, hotfixes, live patches and announcements to match.

SETUP
1. The routine attaches bayov/forever-sim, so the session should start with it checked out (look in the working directory and under /home/user). Use that checkout. Only if it isn't there: call add_repo with owner "bayov", repo "forever-sim", access "push" (load it with ToolSearch if needed), run the clone command it returns, and call register_repo_root with the clone's path. If neither works, carry on with everything that doesn't need the repo, put "no repo access: <the reason>" at the top of the report and in the final reply, and skip Parts 2–4. Never fall back to an anonymous read-only clone for Parts 2–4.
2. In the checkout, check push access: git push --dry-run origin HEAD:refs/heads/forever-update-access-check. If it's denied, carry on with everything else. Save the sim changes and TASKS.md entries as `git format-patch` files, send them with SendUserFile, and put "no push access" at the top of the report and in the final reply.
3. Read tools/forever_update/README.md now. It defines the report format. Read docs/data_sources.md too: it's the registry of every source the repo pulls game data from, the URL of each, the script that fetches it, and which source wins when two disagree.

SCOPE — WoW Forever ONLY. Ignore news that is only about other versions: retail/The War Within/Midnight, Classic Anniversary (TBC or otherwise), Classic Era, Season of Discovery, Hardcore, MoP/Cata Classic, etc. If a source mixes versions, extract only what applies to WoW Forever. If it's unclear whether a change applies to Forever, leave it out or flag it explicitly as unclear.

TIME WINDOW — cover everything published in roughly the last 24 hours (since about 8 PM Israel time yesterday). Each run starts fresh with no record of earlier runs, so include an item from 24–36 hours ago only if it seems to have been posted late or updated, and mark it "may repeat yesterday" ("repeat": true in report.json). Put the publish date on every item.

PART 1 — NEWS. Do thorough research with many separate searches, and fetch the actual pages rather than relying on snippets. At minimum check:
- Official Blizzard: news.blizzard.com (World of Warcraft / Forever articles, patch notes, hotfix posts), the official WoW Forever forums and blue posts (blue tracker).
- Wowhead news for WoW Forever, including datamined beta/live build changes and new build numbers.
- Icy Veins WoW Forever news and class guides, Warcraft Tavern Forever news, Mobalytics WoW Forever.
- Community discussion (e.g. Reddit) only to find official or datamined sources, never as a source of truth itself.
Search specifically for: patch notes, hotfixes, new client builds, beta build changes, class changes, talent changes, ability/coefficient/tuning changes, item and set-bonus changes, racial changes (including the new Skyborne race and new race/class combos), dungeon/raid tuning, server/realm news, and release-schedule news.

PART 1B — NEWLY REVEALED HIDDEN ITEMS. Blizzard ships most Forever items encrypted/hidden in the client, and they get revealed one by one as the server sends their data to players. https://foreverchanges.pro/hidden-items tracks this: revealed/hidden counters (overall, new Forever items, Classic, Season of Discovery), a "Latest items revealed" list grouped by reveal date range (newest group first, e.g. "October 8 to 9"), "A Classic item that changed" comparisons, raid/dungeon/tier-set tables (set pieces show "Item <ID>, still hidden" until revealed), the Forever-only sets and the list of encrypted content groups. Every item links to https://foreverchanges.pro/item/<ID> with its full tooltip.
1. Fetch the page's raw HTML (curl -sS -A 'Mozilla/5.0' https://foreverchanges.pro/hidden-items). It is Next.js server-rendered, so the data sits in the self.__next_f.push([1,"..."]) chunks. JSON-decode and join them with the repo's reader, tools/sources/foreverchanges.py: `fetch('/hidden-items')` then `payload()` (read it first, and tools/database/foreverchanges/scrape.py for how it picks JSON objects out of the payload). Collect every item ID on the page (/item/<6 digits>) with its name, item level, slot and reveal-date group. If curl is refused (for example a 403 from the network proxy), say so in the report and fall back to WebFetch: page through the whole thing with offset and ask for every entry verbatim. Never rely on a summary that may drop items.
2. assets/database/hidden_items.json lists the items that were still hidden at our last local run (tools/sources/hidden.py). An item revealed since then that it marks "simStats": "classic" or "partial" is in the sim with Classic's or only part of its stats, so its real stats are a sim change worth a PR line even when it looks minor. Each run starts fresh, so decide what is "newly revealed" two ways: (a) the reveal-date groups that fall in the TIME WINDOW, and (b) any revealed item whose ID is missing from the repo (grep the ID in assets/database/db.json, tools/database/forever_items.go and assets/db_inputs/*.json) or whose stats differ from what the repo has. Also report movement in the counters and any tier/Forever-only set piece that changed from "still hidden" to revealed.
3. For each new item that a sim-covered spec could wear or that changes a set bonus, fetch https://foreverchanges.pro/item/<ID> for the full tooltip (stats, weapon damage/speed, armor, required level, binding, slot, effects, set bonuses, source/drop location if known, quality, icon name if the page has one). Cross-check with the Wowhead Forever tooltip (https://nether.wowhead.com/forever/tooltip/item/<ID>?dataEnv=16&locale=0, Forever is dataEnv 16) when it exists. www.wowhead.com pages (item, NPC and listing pages) sit behind a bot check and a rate limit, so a plain fetch gets a 403. Use the tooltip API for single items. When a full www page is needed, use the repo's tools/database/forever_wowhead/wowhead.py (its scrape-wowhead skill) for a handful of pages at most, and if that fails too (it needs Chrome), skip it. Never run the full Wowhead scrapes (scrape.py, recipes.py) here: they take hours and run locally. When Wowhead clearly has new Forever items, recipes or vendors, add a TASKS.md line "Run /scrape-wowhead locally" instead. Label these "client" (client data from revealed items), unless only a tooltip-style line with no stats is known.
4. Flag anything balance-relevant: best-in-slot candidates or upgrades for shaman, paladin and rogue first (weapon speed and DPS for Enhancement/Ret/rogue, spell power/healing, hit/crit, set bonuses), then other classes; Classic items whose Forever stats changed; set bonuses that are now visible.

PART 2 — FOREVER-SIM IMPACT. Do this only when Part 1 found game-mechanic changes (class, talent, ability, item, enchant, racial, stat, combat-rule or build changes) or a new client build, or Part 1B found newly revealed or changed items the sim's specs could use:
1. Work in the checkout from SETUP. The repo is a fork of wowsims/classic: Go sim code under sim/, data under assets/ and tools/database/, Forever notes in forever-wiki/, notes.md, shaman_audit.md, beta_handoff.md, TASKS.md. Read notes.md, beta_handoff.md, TASKS.md and the start of shaman_audit.md first. They hold my standing rules: rank sources as docs/data_sources.md's "Which source wins" does (the Forever client/beta itself, then Season of Discovery, then Anniversary and 2019 Classic), never cite vmangos, and never change the sim on a tooltip alone. Also read forever-wiki/sim-status.md (the bullets on ForeverChanges item data and beta build items) for how Forever items get into the database.
2. Find the newest WoW Forever client build number. `python3 tools/sources/wago.py latest --probe 300` prints the newest one wago.tools has. Also check Wowhead datamining posts, Blizzard notes, build trackers and the build shown on foreverchanges.pro, then compare it with the builds the repo already references (grep for 5-digit build numbers like 70291 / 70338 and for "build", and check TASKS.md).
3. For raw client data of the newest build, use wago.tools through the repo's fetcher: `python3 tools/sources/wago.py fetch <build> --set client_update` downloads the tables, `python3 -I tools/sources/db2diff.py <old> <new> <out.md>` writes the diff grouped by class, and `python3 -I tools/sources/wago.py diff <old> <new> <Table...>` compares single tables. Run anything that reads the CSVs with python3 -I. If wago.tools is refused, do NOT try to reach it any other way (no scripts, mirrors or caches). Use Wowhead's Forever tooltips (dataEnv 16), its spell/item pages (see the bot check note in Part 1B) and datamining posts instead. Also use any wago.tools CSV exports committed to the repo (e.g. under assets/db_inputs/) for a build newer than the one the sim was built from.
4. For each relevant change, find where the sim models it (grep spell IDs, names and constants; sim/<class>/, item/enchant data and overrides, notes.md "Need to Verify"), compare the current values with the new data, and decide the change: file and function/constant, old → new, and which notes.md / shaman_audit.md items it settles or affects (cite item numbers). Also catch other changes in the newest build that the sim models, even ones no news site covered.
5. For newly revealed items from Part 1B: new gear goes into ForeverItems, and changed Classic/Forever items into ForeverSeenInGame, in tools/database/forever_items.go, following the conventions there (stats typed from the tooltip, a source when one is known, required level as the tooltip gives it). Then regenerate the database with the repo's tooling (go run ./tools/database/gen_db -outDir=assets -gen=db, as the scraper's header says). Rating stats with no known conversion, chance-on-hit or use effects the sim doesn't model, and set bonuses that need new code go under "Not included — needs your call", unless the effect is a plain stat. If a level-appropriate gear search or preset would change because of a new item, say which spec and by how much, but don't change the shipped gear sets in the PR; list it as a suggestion.

PART 3 — PULL REQUEST. Do this when Part 2 found sim changes backed by official patch notes, hotfixes, blue posts or client data (revealed item data counts as client data):
1. Before starting, list the open PRs with the REST API (GraphQL isn't available in cloud sessions, so `gh pr list` fails): gh api "repos/bayov/forever-sim/pulls?state=open" --jq '.[] | [.number,.title,.head.ref] | @tsv'. If gh is missing or unauthenticated, use the GitHub MCP tools (mcp__github__list_pull_requests, mcp__github__create_pull_request) instead. If an earlier open PR from this task already contains a change, don't duplicate it; mention that PR in the report.
2. Fetch the latest master, then create a branch named forever-update/<YYYY-MM-DD> (add the build number if there is one).
3. Implement the changes in the style of the surrounding code. Keep them to sim/**, proto/**, ui/**, assets/**, tools/database/** and the *.results goldens. Do NOT edit notes.md, shaman_audit.md or beta_handoff.md, because other sessions own them. Put those follow-ups in the PR description instead.
4. Leave OUT of the PR anything that rests only on a tooltip, is datamined but unconfirmed, or is ambiguous. List each of those in the PR description under "Not included — needs your call", with the reason, and add them to TASKS.md (Part 4).
5. Install the toolchain if it's missing (Go >= 1.21, protobuf-compiler, protoc-gen-go; see README), run gofmt -w ./sim, then go test --tags=with_db ./sim/... . If downloading Go modules fails, don't work around it: open the PR as a draft and say the environment's network settings need proxy.golang.org, sum.golang.org and storage.googleapis.com. If goldens change, read the diff of every changed *.results file and confirm each change is explained by today's edits before running make update-tests and re-running the tests. Every test must pass. If the tests can't be made to pass or the toolchain can't be built, open the PR as a draft and say exactly why.
6. Commit with a clear message, push the branch, and open the PR against bayov/forever-sim master: gh api repos/bayov/forever-sim/pulls -f title="..." -f head="forever-update/<date>" -f base=master -f body="..." (add -F draft=true for a draft). Always target bayov/forever-sim with base master, because this is a fork and the default target would be the upstream wowsims repo. Never open anything on wowsims/classic. Never merge the PR yourself.
7. PR title: "Forever update <date>: <one-line summary>". PR description: sources for every change (with their labels), the list of changes (file, old → new), the newly revealed items added (ID, name, key stats), the per-class impact summary (below), the affected notes.md / audit items, the "Not included — needs your call" list, and how it was tested.
If no change qualifies for a PR, don't open one; say so in one line.

PART 4 — TASKS.md. Log follow-up work this run found but couldn't finish by appending items to the end of TASKS.md at the repo root, in the item format the file describes (date — what to do (why/source) [source: <tag>], then indented details). End each item's first line with a source tag: [source: wago build <N>] for a client build, [source: wowhead], [source: foreverchanges], [source: blizzard] (patch notes, dev notes, blue posts) or [source: tooltip]. tools/sources/stale.py finds unprocessed builds by the wago tag, so a build item always carries it. Always add an item when:
- A new WoW Forever client build exists that the repo hasn't processed: "Pull wago.tools DB2 data for build <N> and process it into the sim [source: wago build <N>]". Include the build number, the tables that matter for the sim (e.g. SpellEffect, SpellMisc, SpellAuraOptions, SpellCooldowns, SpellCastTimes, SkillLineAbility, Talent, ItemSparse, ItemEffect, SpellItemEnchantment), direct wago.tools links for that build (e.g. https://wago.tools/db2/SpellEffect?build=<build>), and the spell/item IDs worth checking first.
- A value the sim needs couldn't be confirmed from Wowhead or official sources (list the wago.tools table and ID links to check).
- An item was left out of the PR as "needs your call", or a notes.md / shaman_audit.md follow-up is needed (those files belong to other sessions).
- A newly revealed item couldn't be added (missing stats, unmodeled effect, unknown rating conversion, set bonus needing code): list its ID, name and https://foreverchanges.pro/item/<ID> link.
Before adding, read TASKS.md and skip anything already listed (match on build number or the same spell/item/change); you may add new details to an existing item instead. Never delete or reorder items. Only tick an item in place ([x]) when the repo clearly shows it was settled, and cite the commit or PR on the item.
Commit only TASKS.md, directly to master, in its own commit ("TASKS.md: <short summary>"): fetch origin master first and rebase onto it. If the push races with another commit, fetch, rebase and push again (at most 3 tries). Never force-push. If there's nothing new to log, don't commit.

PER-CLASS IMPACT SUMMARY (in both the PR description and the report): for every class touched today, summarize what changed and what it means. For specs the sim covers (sim/ and ui/ have shaman, paladin, rogue, warrior, hunter, mage, priest, warlock, druid), give the DPS/TPS/HPS change before → after from the golden *.results diffs where they move, and say which spec and preset it is. Shaman, paladin and rogue first.

I am a min-maxer who cares most about BALANCE. I play SHAMAN, PALADIN and ROGUE, and I want every change to those three, however tiny, up front and emphasized. I care about all other classes too and want every balance change surfaced, just lower down.

REPORT CONTENT — every fact goes into report.json (format in tools/forever_update/README.md). The page lays it out in tabs:

1. 🚨 Big changes ("big") — the most important news of the day: major balance passes, big mechanic changes, new builds, release-date or phase news, major content, a big batch of revealed raid or tier items. Leave it empty if there are none. An item belongs here only if it's genuinely big (a new best-in-slot for a sim spec, a tier set revealed); otherwise it goes in Items only.

2. ⚔️ Shaman / Paladin / Rogue ("classes", always all three) — EVERY CLASS change for these three, no matter how small: abilities, talents, coefficients, procs, ICDs, threat, mana costs, racials available to them, and bug fixes affecting them. Give exact numbers old → new whenever the source has them (never round), buff or nerf, and one line on the min-max impact (rotation, gear priorities, caps, weapon speed choices, threat, tank viability). ITEMS DO NOT GO HERE: newly revealed or changed items, weapons and set pieces go only in "items", tagged with who wants them. The page links each class card to its items. If a class has no class changes, give it an empty "changes" list.

3. 💎 Newly revealed items ("items") — today's revealed/hidden counters (with yesterday's count as "prev" when you know it), then every newly revealed item worth knowing as an ITEM entry. The page gets name, stats and icon from Wowhead by ID, so give the id, "who" (classes, with a spec in front when it matters, e.g. "Ele Shaman"), "changed" for Classic items whose stats changed (old → new), group, source, set, whether it's in the sim, and a one-line "take". Set pieces that are no longer hidden go here too. Put the count of skipped irrelevant items in "skippedTitle" (e.g. "Skipped: 23 more cosmetic or low-level items"). If nothing new was revealed, leave "list" empty.

4. 🛠 forever-sim ("sim") — the PR (state, number, link) or why there's none or why it's a draft, the newest build vs the repo's ("build"), the PR's changes, the per-class impact summary ("impact" rows from the golden diffs, with exact numbers, plus "impactNote"), "Not included — needs your call", and the items added to TASKS.md today ("tasks").

5. 📊 Other classes ("other") — every balance change for the remaining classes, by class, with exact numbers. Class changes only; their items also go in "items".

6. 📰 Everything else ("misc") — smaller details: systems, dungeons and raids, professions, quests, UI, bug fixes, beta waves and Server Slam, realms, dates, known issues. One row each, with a category; put long details in "details".

7. Sources ("sources") — the links used, labelled by site.

Give every change a status: official (patch notes), hotfix, blue (blue post), interview (developer interview), client (client data), datamined (unconfirmed), tracker (the testers' bug tracker), tooltip (tooltip only) or unclear. Never present datamined or rumored changes as confirmed. Say when something rests only on a tooltip. Keep exact numbers everywhere (never round), and keep every fact the content above calls for.

KEEP IT SHORT AND SCANNABLE. I read this on my phone and want the important things in seconds:
- "tldr" (required, at most 5 points, most important first): one line each, starting with a tag (Sim, Shaman, Paladin, Rogue, Build, Items, News, ...). Mark with "hot": true only what needs my attention or changes the sim. On a quiet day, 1–2 points are enough.
- "simTodo" (required whenever anything touches the sim): one row per sim change, saying exactly what to change: "what" (in a few words), "where" (file · function or constant), "old" → "new", a status label, a "state" (pr = in today's PR, call = needs my call, task = logged in TASKS.md, done = already in the sim) and a "why" of at most 12 words. This list replaces "sim.changes", "sim.notIncluded" and "sim.tasks"; leave those empty.
- Every "take" is one line of at most 15 words, and every "misc" text at most 25 words. Put anything longer in "details".
- Set "repeat": true on anything from yesterday's report. The page folds those away, so don't repeat their details.
- Leave out news with no gameplay or sim impact (soundtracks, merch, art, speculation); give it one short misc row at most.

REPORT FORMAT — the page is built from report.json by the repo's builder; don't hand-write HTML.
1. Write report.json in your scratchpad, following tools/forever_update/README.md (example: tools/forever_update/example.json). Set "pageTitle" to "Forever Update <Mon D>" (e.g. "Forever Update Oct 13"). Fill "headline" with one or two sentences, and "alerts" with anything that went wrong (no push access, a refused host, a draft PR).
2. Build it: python3 tools/forever_update/build.py <scratchpad>/report.json -o <scratchpad>/forever-update-<YYYY-MM-DD>.html --strict. If it reports problems, fix report.json and build again. When Wowhead has no tooltip for an item yet, give that item "name", "quality", "icon" and "lines" yourself from foreverchanges.pro. Don't edit the template to work around a problem.
3. Publish the built file with the Artifact tool as a NEW artifact each day (a new file path each day), with icon "news" and a one-sentence description of the day's headline. Don't load design skills or restyle the page; the template already follows the artifact page contract.
4. If the Artifact tool is unavailable or publishing fails, send the HTML file with SendUserFile instead and say so.

FINAL REPLY (pushed to my phone as the notification): 2–4 short lines: the top tldr point, one line for shaman/paladin/rogue (or "no S/P/R changes"), the number of newly revealed items worth a look, and the artifact link (plus the PR link if one was opened). When today's PR or a new client build changes something BayovCore takes from forever-sim (items or the database, talents, stat weights, presets, BiS lists, or a build the repo hasn't processed), add one more line: "Then run /update-data locally." Nothing else.

If there is no new WoW Forever news, no new build and no newly revealed items in the window, don't publish an artifact. Reply with a single short line saying so, with the date, and nothing more.
